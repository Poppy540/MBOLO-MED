## 2. Constat chiffré et cause identifiée
- **Constat** : `pnpm audit --prod` signale 1 faille haute, GHSA-ch52-4w7c-c8xp (CWE-524, CVSS 3.1 : 7,5), dans `http-cache-semantics` ≤ 4.2.0. Le contrôle de la CI (`pnpm audit --prod --audit-level high`) échoue donc sur toutes les demandes de fusion. **Aucune version corrigée n'est publiée** (`http-cache-semantics` 4.2.0 est la dernière ; `make-fetch-happen` 16.0.1, la dernière, en dépend toujours).
- **Chaîne** : `@mbolo/drapeaux` → `unleash-client` 6.12.1 → `make-fetch-happen` 15.0.6 → `http-cache-semantics` 4.2.0.
- **La faille** : un **cache HTTP partagé** bâti sur ce paquet peut rendre à un attaquant, qui envoie lui-même une requête avec un `max-stale` élevé, une réponse mise en cache pour un autre utilisateur (dont ses cookies de session).
- **Pourquoi elle n'est pas exploitable ici** (confiance élevée, lecture du code de `unleash-client` 6.12.1) :
  - `unleash-client` appelle `make-fetch-happen` **sans emplacement de cache** (`cachePath` absent) : aucune réponse n'est mise en cache ;
  - ce client ne fait que des appels sortants vers notre serveur Unleash (état des flags, identique pour tous, jeton de service) ; aucun tiers ne peut y faire passer ses propres requêtes ;
  - aucune donnée de patient, aucun cookie d'utilisateur ne transite par lui.

## 4. Options
### Option A — Exception documentée et surveillée
- **Description** : ignorer cette seule faille dans `pnpm audit` (`pnpm.auditConfig.ignoreGhsas` du `package.json` racine), l'inscrire dans `docs/securite/scans.md`, ajouter un test qui échoue si `unleash-client` active un jour un cache HTTP, réexaminer chaque semaine et retirer l'exception dès qu'un correctif paraît.
- **Coût** : quelques lignes ; aucune dépendance ajoutée.
- **Délai** : immédiat.
- **Limites** : repose sur l'analyse du code actuel de `unleash-client` (le test la protège contre une mise à jour) ; l'alerte Dependabot reste à fermer à la main.

### Option B — Remplacer `unleash-client`
- **Description** : lire l'état des flags par un petit client maison sur l'API d'Unleash, branché à OpenFeature.
- **Coût** : une demande de fusion plus lourde, du code de plus à maintenir et à tester (stratégies de ciblage par cohorte, ville, spécialité).
- **Délai** : plusieurs jours.
- **Limites** : réimplémenter des règles de ciblage est une source d'erreurs d'activation, alors que la faille n'est pas exploitable.

### Option C — Attendre un correctif
- **Description** : ne rien changer.
- **Coût** : nul.
- **Délai** : inconnu.
- **Limites** : le contrôle de la CI reste rouge pour toutes les demandes de fusion ; un vrai problème de dépendance pourrait passer inaperçu au milieu de ce rouge permanent.

## 5. Recommandation
- **Option recommandée** : A.
- **Argumentation** : la faille vise un cache partagé que nous n'avons pas ; l'exception est étroite (un seul identifiant), visible, testée et datée ; elle garde le contrôle de la CI utile pour toute autre faille.
- **Données utilisées et sources** : `pnpm audit --json` et `pnpm why http-cache-semantics` (2026-10-03) ; `npm view make-fetch-happen`, `npm view http-cache-semantics` (2026-10-03) ; code de `unleash-client` 6.12.1 (`lib/request.js`, `lib/repository/bootstrap-provider.js`).
